# 004 — 模型失败恢复：重试从未执行，重试权收回插件

时间：2026-09-13 03:31（本机时区）
状态：已实现并验证（`pnpm build` + `test:model-recovery` 62 项 + `test:retry-repro` 8 项全绿）

## 起因

用户报告：Kenari 模型调用失败切换模型时「没有多次重试？」。会话启动通知里能看到
`kenari/glm-5-3-flash → kenari/deepseek-v4-flash` 这类换模型通知。

## 诊断（结论先行）

**确认：dsh 自带的重试一次都没有执行过，换模型发生在第一次失败上。** 证据全在真实会话日志里：

- `~/.dsh/sessions` 下全部 8 个会话的 `llm/retry` 与 `llm/retry-started` 事件数都是 0。
- 9 月 11 日那次（`session-9e37cf73…`，webrtc-apple 工作区）：失败码 `TRANSPORT`（`"Connection error."`，
  0 token），换模型通知在失败后 **9ms** 落地，下一次 `request/header` 在 **5015ms** 后发出 ——
  正好一次 `modelSwitchDelayMs`，而非 5 次固定 5s 的下限 25s。
- 该会话 `assistant/attempt` 只有 2 条，每个失败模型各一次。

排除项（避免走弯路）：`llm-retry` 确实在 web profile 里（153 条中的第 17 条，未 disabled）；
`providers.kenari.retryPolicy` 确实进了 `--dump-config`；`TRANSPORT` 在默认可重试码里；
`preparedCall` 缺失（`retryPolicy === undefined`）这条路不可能 —— 它只在 `NO_ADAPTER` 时成立，
而那条路产出的是 `NO_ADAPTER` 结束帧、发不出网络请求，与实测的真实网络失败矛盾。

**根因**：`agent/request-error` 是没有默认行为的瀑布，不调用 `next()` 的监听器会否决它后面的一切。
插件（`src/llm/recovery.ts`）正是这样一个监听器，所以：

1. 它一介入就把 `dsh-llm-retry` 连同下游（compaction 等）一起饿死；
2. 只要注册顺序被 live reload 翻过来一次（profile 里 `patchReload: live`，插件是靠 `insert` 追加到
   树尾的），llm-retry 就永久出局，而插件观察不到自己的顺序。

设计文档 §4.1 把「5 次重试」建立在这个运行期条件上，而 §7.d 只验证了策略形状、没有端到端复测。

## 改动

| 改动 | 位置 |
| --- | --- |
| 监听器先 `await next()`，链上决定重试就原样放行；下游抛错记 warn 后继续本地恢复 | `src/llm/recovery.ts` |
| 新增阶段 0：同路由重试 `modelRetryMaxRetries` 次、间隔 `modelRetryDelayMs`，预算**按路由**计算 | `src/llm/recovery.ts` |
| 链上本轮已排程过重试时让位（数会话里的 `llm/retry`），两条机制不各数一遍 | `src/llm/recovery.ts` |
| Kenari 路由关掉 dsh 重试：`retryPolicy.maxRetries: 0`；插件自带适配器用 `dshRetryDisabledPolicy()` | `cordis.patch.yml`、`src/llm/retry.ts`、`src/index.ts` |
| 换模型排除本 step 已失败过的路由（修 glm-5-3-flash ↔ nemotron 同窗口横跳） | `src/llm/recovery.ts`、`src/llm/candidates.ts` |
| 新增 `modelRetryNoticeEnabled`（默认 true）：开始重试时注入一条说明 | `src/index.ts` |
| 新增 `test/retry-repro.mjs`；`test:model-recovery` / `test:retry-repro` 接入 scripts | `test/`、`package.json` |

`kenariRetryPolicy()` 被 `dshRetryDisabledPolicy()` 取代 —— 重试预算从「patch 与 Config 两处、需手工同步」
变成单一来源。设计文档新增 §10「实测修正」，逐条列出被推翻的旧结论。

## 验证

- `pnpm build`（tsc + client 校验）通过。
- `node test/model-recovery.mjs` → 62/62。
- `node test/retry-repro.mjs` → 8/8，三个场景：
  - A 出厂配置：每条路由 1 + 5 次尝试后才升级，`llm/retry` 为 0，重试有通知解释；
  - B 该路由 dsh 重试开着、插件在内层：llm-retry 重试 5 次，插件不叠加预算；
  - C 同 B 但插件被排到外层（复刻 live reload）：llm-retry 仍重试 5 次 —— 守住不再饿死。
- 其余离线套件（default-route / catalog-view / favicon / session-title）不受影响，均通过。
- 未跑 `pnpm test`（`test/real-harness.mjs` 需要真实 key 并会产生计费调用）。

## 遗留

1. **需要重启 dsh 才生效**：`cordis.patch.yml` 的 patch 与适配器注册时机都要求重启；改动过的
   `providers.kenari.retryPolicy` 在适配器注册时被 dsh 冻结。
2. **升级阶段的等待仍无 `llm/retry` 节点**：Kenari 路由上 dsh 的重试已关，界面上重试与换模型都表现为
   「一次失败的尝试 → 通知 → 新尝试」。这是有意的（不补写 `llm/retry` 会污染 llm-retry 的投影计数）。
3. **`agent.inject` 有丢失风险**（dsh 的 `Agent.inject` 注释：可能错过已 claim batch 的那次请求），
   换模型通知与重试通知都走它。dsh 自己的模型切换通知走 `agent/pre-step` 追加，更稳；本次未改，
   若观察到通知偶发不出现，改走 pre-step 是下一步。
4. **同 step 内换过模型后，dsh 的计数不会重置**（key 是 provider + policyKey，不含模型）——
   现在重试由插件按路由记账，这个坑对插件自身不再成立；但若用户把该路由的 `retryPolicy` 重新打开，
   dsh 侧的计数语义仍是按 provider，需要按 §10.4 重新评估。
