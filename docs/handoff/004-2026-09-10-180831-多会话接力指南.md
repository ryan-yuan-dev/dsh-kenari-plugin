### 2.3 第 1 期直接相关的源码事实（浓缩，详细见知识库）

- `DeepSeekSearchProvider` 构造参数是 **thunk** `() => DeepSeekSearchProviderOptions`；`available()` 判定 = 有 `apiKey` 或有 `resolveApiKey` 且 `URL.canParse(baseURL)`。兜底实例必须传 `resolveApiKey`（每次现场解析 `DEEPSEEK_API_KEY`），否则有 key 也判不可用
- `HttpFetchProvider` 构造 `(limits, resolveAddresses?)`，第二参数有默认值，只传 limits 即可；limits 5 字段：maxResponseBytes / maxBodyChars / timeoutMs / maxRedirects / userAgent
- 两个兜底类从包入口 import：`@deepseek-ai/dsh-web-search-deepseek`、`@deepseek-ai/dsh-web-fetch-http`（peer 已在 package.json 定版）。**只实例化，绝不 `register*Provider`**（id 冲突 `WEB_DUPLICATE_PROVIDER`）
- 官方 key 读取模式（照抄）：`ctx.get('credentials')` 优先，seam 缺失时回退 `launchEnvironmentOf(ctx)`；`credentials.resolve/describe` 都是 **async**
- `@deepseek-ai/schemastery` API 形状：`z.string().role('credential-ref').default(...)`、`z.number().step(1).min(n).default(...)`、`z.boolean().default(...)`
- peer 安装坑：新加 `@deepseek-ai/dsh-*` peer 后，若 pnpm 报 `minimumReleaseAge` 供应链策略拦截，往仓库根 `pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 加对应 `pkg@0.1.5-rc.1` 条目（现有 22 条可参考）

### 2.4 测试与计费纪律

- `web_search`/`web_fetch`/`x_search` 按次计费到真实余额。**测试前确认 key 余额，优先用最小调用量**；失败调用不计费
- 当前 `~/.dsh/.credentials.yaml` 中**尚未配置 `KENARI_API_KEY`**。第 1 期验证前需要用户拿到 `kn-` key 并配置（凭据 seam 或环境变量）；没有 key 时 `available()` 为假，web 调用会直接走兜底——这本身就是验证点之一
- `DEEPSEEK_API_KEY` 是否已配置未核实；第 1 期验证 3（配了官方 key 仍走 Kenari）依赖它
