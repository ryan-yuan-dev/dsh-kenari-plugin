# 模型调用失败自动恢复（重试 + 换模型 + 回退默认 provider）

日期：2026-09-11
状态：设计待审阅
版本基线：dsh `0.1.5-rc.1`（源码 tag `dsh-v0.1.5-rc.1`）
前置阅读：`docs/knowledge-base/plugin-rules.md`、`docs/knowledge-base/dsh/dsh-source-verified.md`

## 1. 目标

会话运行中，Kenari 路由的模型调用失败时自动恢复，不让人工介入：

1. **重试**：失败后 5s 重发，自动重试 5 次。
2. **换模型**：重试仍失败，换一个上下文窗口 >= 当前模型的模型。
3. **回退默认 provider**：换模型仍失败，回退到 dsh 默认 provider/model。
4. 上述都失败，才让该轮以 error 结束（现状行为）。

**范围**：只对 Kenari 路由生效（默认 `kenari`（llm-pi-ai 预设）与 `kenari-direct`（插件自带适配器））；其他 provider 的会话行为完全不变。

## 2. 决策记录

三个决策由用户拍定，记录理由以免后人重开：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 是否发「继续」消息 | **不发** | 重试发生在同一个 step 内，该轮不中断，模型拿回控制权后自然继续执行。此时再发「继续」会额外开一轮对话，可能让模型重复干活。 |
| 生效范围 | **仅 Kenari 路由** | 不改变其他 provider 的会话语义；最终兜底到默认 provider 已经覆盖「Kenari 整体不可用」的情形。 |
| 换模型候选 | **同类里最小够用** | 先在同一 provider 内挑 `contextWindow >= 当前` 的最小者；同 provider 无候选再跨 provider 找。避免为一次失败切到又贵又慢的最大上下文模型。 |

## 3. 事实基础（vendor 源码实读）

以下每条都是本次核对过的源码事实，不是推测。行号对应 submodule tag `dsh-v0.1.5-rc.1`。

### 3.1 任何适配器失败都会进入 `agent/request-error`

`LlmRuntime` 捕获适配器与迭代过程中的一切抛错，转成终态 `finish` chunk：

```ts
// packages/llm/llm/src/index.ts:1124-1132
function adapterFailureChunk(error: unknown, signal?: AbortSignal): StreamChunk {
  const failure = normalizeLlmFailure(error)
  return {
    type: 'finish',
    reason: signal?.aborted || failure.code === 'ABORTED'
      ? { kind: 'aborted', failure }
      : { kind: 'error', failure },
  }
}
```

**这条很关键**：它在 `adapterStream` 的两个位置被 yield（`index.ts:1061`、`index.ts:1076`），覆盖「第一个 chunk 之前就抛」（HTTP 401/402/429/5xx）与「流中途抛」两种情形。所以 agent loop 不会因为适配器抛错而直接崩掉该轮，而是走到：

```ts
// packages/core/agent-loop/src/agent.ts:441-464
const finish = live.finish
if (finish.kind === 'error' || finish.kind === 'aborted') {
  live.settle('assistant/attempt', () => this.session.append('assistant/attempt', {...}).seq)
  const action = await this.dispatch.waterfall(
    'agent/request-error', {
      turn, step,
      provider: request.provider,
      failure: finish.failure,
      retryPolicy: preparedCall?.retryPolicy,
      signal,
    },
    () => Promise.resolve<RequestErrorAction>(undefined),
  )
  signal.throwIfAborted()
  if (action?.kind !== 'retry') {
    throw new LlmError(finish.failure.message, finish.failure.code, finish.failure)
  }
  continue
}
```

`continue` 回到同一个 `while (true)` 顶部，也就是说**重试不结束该 step**。

### 3.2 重试是 dsh 自带能力，`dsh-llm-retry` 已在 web profile 上

`dsh --profile web --dump-config` 第 51-52 行：

```yaml
- id: llm-retry
  name: '@deepseek-ai/dsh-llm-retry'
```

它监听 `agent/request-error`，按适配器注册时捕获的策略决定是否重试：

```ts
// packages/llm/llm-retry/src/index.ts:215-224
} else if (!policy.retryableCodes.includes(failure.code)) {
  return next()
}
const previous = retryState[retryStateKey(provider, policyKey)]
const previousRetry = previous?.retry ?? 0
if (policy.mode === 'normal' && previousRetry >= policy.maxRetries) return next()
```

**决定重试时它不调用 `next()`**，所以排在它下游的监听者收不到该次失败；只在「码不可重试」或「次数用尽」时才 `next()`。这正是我们要的：重试托管给 dsh，升级逻辑接在它放弃之后。

退避延迟（`packages/llm/llm-retry/src/index.ts:59-64`）：

```ts
function localDelay(config: ResolvedRetryPolicy, retry: number, random: () => number): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}
```

**「每次固定 5s」是可以精确表达的**：`initialDelayMs: 5000, maxDelayMs: 5000, jitterRatio: 0` 时每次都是 `min(5000*2^(n-1), 5000) * 1 = 5000`。不需要新增「固定延迟」概念。

默认策略（`packages/llm/llm/src/retry-policy.ts:14-24`）：`maxRetries: 5`、退避 500ms→10s、可重试码 `EMPTY_RESPONSE / RATE_LIMIT / SERVER / TIMEOUT / TRANSPORT`。注意 `AUTH`、`QUOTA`、`CONTEXT_WINDOW_EXCEEDED`、`INVALID_REQUEST`、`MISSING_CREDENTIAL` **不在**默认可重试集内。`retryableCodes` 不允许为空数组（`retry-policy.ts:170-171` 抛错）。

重试计数是按 `[provider, policyKey]` 存的（`llm-retry/src/index.ts:66-81`），并在 `step/start` / `turn/end` 重置（`llm-retry/src/index.ts:131-137`）。推论：**同 provider 换模型不会重置计数**（换完立刻又是「用尽」状态，直接轮到我们的升级逻辑）；**跨 provider 会重置**，新 provider 天然获得一整轮重试。

重试在 Web UI 里可见：`ui-chat` 有专门的会话节点渲染 `llm/retry` / `llm/retry-started`（`packages/client/ui-chat/src/client/conversation-nodes/retry.ts`）。这是选择复用 dsh 机制、而不是自己写循环的主要理由——自建循环会让这 25 秒在界面上毫无解释地卡住。

### 3.3 换模型有正式缝：`agent/request` 瀑布

事件文档原文（`packages/core/agent/src/runtime-types.ts:331-347`）：

> Replace the frozen call configuration. `await next()` yields the config the machine would use …; **return a replacement to switch**.

返回值是 `LlmCallConfig`（`packages/llm/llm/src/call-config.ts:23-30`）：

```ts
export interface LlmCallConfig {
  provider: string
  model: string
  reasoningEffort?: ReasoningEffortId
  temperature?: number
  maxTokens?: number
  stop?: string[]
}
```

**关键时序**：每次 `continue` 都会重跑 `prepareRequest`（`agent-loop/src/agent.ts:361-362, 500-550`），也就是重新派发 `agent/request`。所以在监听器里改 provider/model，对**下一次重试尝试立即生效**，无需触碰会话状态。

### 3.4 与 `installModelSelection` 的覆盖顺序竞争（必须处理）

session-controller 在 agent setup 阶段装了自己的 `agent/request` 监听器，它用**本 step 组装时捕获的**原选择回写：

```ts
// packages/core/agent/src/model-selection.ts:88-105 （installModelSelection）
agentCtx.on('agent/request', async (_payload, next): Promise<LlmCallConfig> => {
  const resolved = await next()
  const selected = selection.assembled          // ← 组装时捕获，重试不会更新
  if (selected === undefined) return resolved
  const { reasoningEffort: _inheritedEffort, ...withoutInheritedEffort } = resolved
  return { ...withoutInheritedEffort, provider: selected.provider, model: selected.model, ... }
})
```

瀑布是「外层先跑、外层拿到最终决定权」。因为 `selection.assembled` 在同一个 step 内不会因重试而更新，**如果我们的监听器排在内层，我们的换模型结果会被它改回原模型**。

解法：用 `ctx.on('agent/request', handler, { prepend: true })` 注册，把自己固定在**最外层**——先 `await next()` 拿到全链结果，再覆盖 provider/model。dsh 自己也用 `prepend` 来抢夺最终决定权（`installModelSelection` 挂 `agent/pre-step` 时就带 `{ prepend: true }`）。

另证：`installModelSelection` 是 agent-scoped（`agent.ctx`）注册，我们这个 root 注册的监听器按 scope 过滤器同样能收到该 agent 的事件（`packages/core/scope/src/index.ts:170-185`：未打标签的监听器全局准入）。

### 3.5 换模型是可溯源的，不用自己造通知

`buildRequest` 在配置变化时以 `reason: 'change'` 追加新的 `request/header`，并同步 `request/context`：

```ts
// packages/core/agent-loop/src/agent.ts:573-585
if (!this.requestHeaderLogged) {
  this.session.append('request/header', { header, reason: baseline === undefined ? 'initial' : 'resume' })
  this.requestHeaderLogged = true
} else if (baseline === undefined || !headerEquals(baseline, header)) {
  this.session.append('request/header', { header, reason: 'change', ... })
}
```

所以换模型后的尝试会留下真实的会话日志记录，而**不是**只在 HTTP 层偷偷换了模型。

## 4. 机制设计

### 4.1 分工

恢复分两段，各由最合适的机制承担：

| 段 | 承担者 | 为什么 |
| --- | --- | --- |
| 5s × 5 重试 | **dsh 自带的 `dsh-llm-retry`** + 声明式 `retryPolicy` | 复用成熟机制，重试在 Web UI 上可见（`llm/retry` 节点），并写入持久会话事件 |
| 换模型 → 回退默认 provider | **插件新增的升级状态机** | 需要跨 attempt 的记忆与对 `agent/request` 的改写，dsh 没有对应 seam |

不自己写重试循环，是刻意的：自建循环会让「失败后静默等 25 秒」在界面上没有任何解释。

### 4.2 重试阶段（声明式，零新代码）

给 Kenari 路由的 `retryPolicy` 设成 5 次、每次 5s：

```yaml
retryPolicy:
  mode: normal
  maxRetries: 5
  backoff:
    initialDelayMs: 5000
    maxDelayMs: 5000
    jitterRatio: 0
```

两个写入点：

1. **llm-pi-ai 的 `kenari` 路由**（默认路径）：写进 `cordis.patch.yml` 的 `providers.kenari`。这是 composition 默认值；`llm-pi-ai` 的 provider profile 是「按 provider route 合并」的，用户仍可在 `llm-pi-ai` 设置节里覆盖 `retryPolicy`。
2. **插件自带适配器 `kenari-direct`**（`nativeAdapterEnabled` 时）：`KenariLlmAdapter` 覆写 `providerRetryPolicy()`，返回由插件 Config 拼出的同一策略。

`retryableCodes` 采用 dsh 默认集（不显式写）。**刻意不把 `CONTEXT_WINDOW_EXCEEDED` 加进去**：同一个模型重试同样的上下文永远会再失败，让这类失败直接落到升级阶段是更快的正确行为。

### 4.3 升级状态机

新增 `src/llm/recovery.ts`，注册两个监听器。

**监听器一：`agent/request-error`（root ctx，默认顺序 → 排在 llm-retry 下游）**

```
输入：{ agent, turn, step, provider, failure: { code, message, status? }, signal }

1. provider 不在 modelRecoveryProviders 内 → next()
2. signal.aborted → next()
3. 取该 agent 的状态；stepKey 变了（换 turn/step）→ 重置为 { stage: 0 }
4. 决定下一个 stage：
     modelSwitchEnabled 为 false        → 放弃：next()
     stage 0 且 code ∈ modelSwitchSkipCodes → stage 2
     stage 0 其余情形                      → stage 1
     stage 1                              → stage 2
     stage 2                              → 放弃：清状态，next()
5. stage 1：候选 = 选一个「上下文 >= 当前」的模型
     候选为空 → 直接降级去 stage 2
6. stage 2：默认选择 = ctx.agentDefaultModel.currentSelection()
     与当前 provider+model 相同 → 放弃：next()
7. 写入 state.override = 目标选择，state.stage = 新 stage
8. 可选：注入一条模型切换通知（见 4.6）
9. await 一个可取消的 modelSwitchDelayMs 延时
10. 延时中被取消 → next()
11. 返回 { kind: 'retry' }
```

**为什么凭据类失败跳过 stage 1**：`AUTH` / `INVALID_CREDENTIAL` / `MISSING_CREDENTIAL` / `QUOTA` 是同账号（同一个 key、同一个余额）的问题，在同一个 Kenari provider 里换模型不会好转，直接去换 provider 才有意义。这个集合是配置字段 `modelSwitchSkipCodes`。

**监听器二：`agent/request`（root ctx，`prepend: true` → 最外层）**

```
输入：{ agent, turn, step, signal }
const resolved = await next()
const override = overrideOf(agent)          // 3.4 节论证的顺序保证
if (override === undefined) return resolved
return { ...resolved, provider: override.provider, model: override.model,
         ...(override.reasoningEffort === undefined ? {} : { reasoningEffort: override.reasoningEffort }) }
```

**状态容器**：`WeakMap<Agent, RecoveryState>`。`RecoveryState = { stepKey: string; stage: 0|1|2; override?: ModelSelection }`。用 WeakMap 是因为 agent 释放后自动回收，不需要手动清理（plugin-rules #11 用 effect 管理资源；这里连 effect 都不需要）。

**状态重置与终止**：

- `stepKey` 是 `${turn}:${step}`。重试停留在同一个 step，所以 stage 与 override 在升级过程中持续累积；换了 step（下一轮对话、或下一个 step）则 stage 归零重新开始。
- 终止条件只有一个：stage 2 之后仍有失败 → 清状态、返回 `next()`（该轮以 error 结束，即现状行为）。**没有无限循环**：一个 step 内最多额外 2 次尝试（换模型、回退 provider）。
- stage 2 的目标与当前 `provider`+`model` 相同时直接放弃——「回退到默认」在已经处于默认时是空操作，重试同一个组合没有意义。
- 状态归零后（新 step）若同 provider 又有候选，会正常再走一遍 stage 1；因为 §4.4 的阈值单调性，不会退回先前窗口更小的模型。

### 4.4 候选模型选择

`src/llm/candidates.ts`，纯逻辑 + 可注入的 `llm` 依赖，便于单测：

```
pickContextSufficient(llm, currentProvider, currentModel, currentWindow) -> ModelSelection | undefined

1. 阈值 = currentWindow ?? 0        // 拿不到就当作 0，任何已知窗口都够用
2. 先在同一 provider 内找：listModels(currentProvider)
     排除 currentModel 本身
     解析每个模型的 contextWindow；要求「已知且 >= 阈值」
     取 contextWindow 最小的一个（同值按 id 字典序，保证确定性）
3. 同 provider 无候选 → 遍历 ctx.llm.listProviders()（排除 currentProvider），同法找
4. 都无 → undefined
```

`currentWindow` 优先取 `agent.session.requestContext().contextWindow`，缺失时回退 `resolveModelInfo(currentProvider, currentModel)`。

枚举结果按 `catalogCacheTtlMs`（已有配置字段）缓存，避免每次失败都打一遍「所有 provider × 所有模型」的元数据解析。语义上这是「模型元数据可信多久」，与该字段原意一致，不新增配置。

两点行为说明：

- **阈值单调**：stage 1 的阈值始终是「当前（可能已被换过）模型」的窗口，所以一次会话里不会来回横跳回先前那个窗口更小的模型——换过去的模型窗口只会持平或变大。
- **跨 provider 候选无法预判凭据**：Kenari 之外的候选是否可用取决于它自己的 key，插件拿不到（provider 的 `apiKeyEnv` 不在 `ctx.llm` 的公开面上）。凭据缺失时该次尝试会以 `AUTH` 失败并继续走 stage 2，属于可接受的代价。

### 4.5 override 的生命周期

| 事件 | 行为 |
| --- | --- |
| 决定换模型/回退 | 写入 `override` |
| 之后所有 `agent/request` | 持续套用 → 该会话后续 step 都用新模型（否则下一步就退回失败的原模型） |
| 用户显式选模型（会话日志追加 `model/selection`） | 清除 `override` —— 人工选择优先 |
| agent 释放 | WeakMap 自动回收 |

监听 `session/event`，遇到 `type === 'model/selection'` 时清除对应 agent 的 override。`consumeSelection` 不会追加该事件（它只清 session-controller 自己的 pending 缓存），所以不会误清。

### 4.6 模型切换的通知

换模型对用户是可见的行为变化（回答风格、能力都会变），静默切换会让人困惑。dsh 自己的做法是往会话里追加一条带 `form: 'notice'` 的插件 user 消息（`packages/core/agent/src/model-selection.ts:41-56`）。本设计复用同一形态：

```ts
agent.inject(createUserMessage({
  content: [{ type: 'text', text: '[kenari: <原因> 连续失败，模型已从 X 切换到 Y]' }],
  source: { kind: 'plugin', plugin: 'kenari', form: 'notice', summary: 'X → Y' },
}))
```

`inject` 把消息排到下一个 step 的 pre-step（不唤醒 driver），所以重试成功后模型能读到它，知道自己的路由变了。由 `modelSwitchNoticeEnabled` 控制。

## 5. 配置字段

全部按 plugin-rules #10 声明为 Schemastery 配置字段（能不改代码就通过配置改掉）。

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `modelRecoveryEnabled` | bool | `true` | 总开关；关掉则完全退回现状 |
| `modelRecoveryProviders` | string[] | `['kenari', 'kenari-direct']` | 参与恢复的 provider 路由 |
| `modelRetryMaxRetries` | int | `5` | 重试次数（`kenari-direct` 路由；pi-ai 路由见 §4.2） |
| `modelRetryDelayMs` | int | `5000` | 每次重试的等待（同上传导范围） |
| `modelRetryableCodes` | string[] | dsh 默认集 | 可重试的失败码 |
| `modelSwitchEnabled` | bool | `true` | 是否允许换模型；关掉则只重试，重试用尽后该轮按现状以 error 结束 |
| `modelSwitchDelayMs` | int | `5000` | 换模型/回退前的等待 |
| `modelSwitchSkipCodes` | string[] | `['AUTH','INVALID_CREDENTIAL','MISSING_CREDENTIAL','QUOTA']` | 跳过「同 provider 换模型」直接回退 provider 的失败码 |
| `modelSwitchNoticeEnabled` | bool | `true` | 是否注入模型切换通知 |

`modelRetryableCodes` 不能是空数组（dsh 的 `resolveRetryPolicy` 会抛错），schema 层加校验（`validate` 钩子或 `.min(1)`）。

`reasoningEffort` 的传递规则：**stage 1 换模型时不继承原模型的 `reasoningEffort`**——档位是 adapter-owned 的、按模型定义的，把 A 模型的档位写给 B 模型可能直接非法。stage 1 的候选只写 `{ provider, model }`，让新模型走自己的默认；stage 2 的默认选择来自 `agentDefaultModel.currentSelection()`，带出的 `reasoningEffort` 本身就是为该模型配置的，原样保留。

## 7. 验证方式

沿用仓库既有测试形态（`test/*.mjs`，node 直跑，零计费）。

**a. 候选挑选（纯函数组）**
注入假的 `llm`（`listProviders` / `listModels` / `resolveModelInfo`），断言：
- 同 provider 有多个候选时取上下文最小的那个
- 同 provider 无候选时跨 provider 找
- 当前窗口未知（无 `context` 元数据）时不崩、不误选
- 全无候选返回 undefined

**b. 升级状态机（真实 cordis Context + 脚本化失败）**
照 `test/real-harness.mjs` 的做法起 `Context`、`provide` 假的 `llm` / `agents` / `agentDefaultModel`，然后：
- 第一次失败 → 断言 `agent/request` 的覆盖变成「同 provider 最小够用模型」，且返回 `{kind:'retry'}`
- 第二次失败 → 断言覆盖变成默认 provider/model
- 第三次失败 → 断言返回 undefined（放弃）
- `modelSwitchSkipCodes` 里的码 → 断言直接跳到默认 provider，不做同 provider 换模型
- `modelRecoveryEnabled: false` → 断言监听器完全不介入

**c. 覆盖顺序回归（这条必须有）**
在 `installModelSelection` 之后注册一个「用组装时捕获的原模型回写」的监听器，断言最终到达适配器的是我们的覆盖值。这是 §3.4 那个竞争的可执行证据；如果 dsh 升级改变了瀑布顺序，这条会先红。

**d. 刻意不做：不挂载 dsh 的 agent loop 去复测重试**
重试是 dsh 自身机制的**声明式配置**，`dsh-llm-retry` 的行为属于 dsh 的测试范围。为复测它而把 agent loop、session-projection 一并挂进来，会给插件绑上一堆与自身逻辑无关的宿主内部依赖，dsh 一升级就红，而且红的原因不是我们的 bug。所以重试侧只验证三件事：我们产出的策略形状（a 组 + `resolveRetryPolicy` 的校验）、patch 层确实把它写进了 `providers.kenari`（`--dump-config` 确认）、以及我们的升级状态机在**真实 cordis 作用域派发**下被正确调用（b、c 组用 `agentEvents` 驱动，复刻 agent loop 的 `agent/request-error` → `{kind:'retry'}` → `agent/request` 契约）。

**e. 配置校验**
`modelRetryableCodes: []` 必须在加载期报错而不是运行期崩。

## 8. 已知限制与风险

1. **可能重复计费**：`TRANSPORT` 类失败（连接中断）在服务端可能已经完成并计费，重试按 Kenari 规则会造成第二次计费。风险来自需求本身（要求重试）；缓解手段是 `modelRetryableCodes` 可配置。注意与 plugin-rules #14 的区别：#14 针对按次计费的生成类端点（客户端超时不得重试），本条是 chat 按 token 计费。该限制写入 README。
2. **跨 provider 回退会重置重试计数**：换到默认 provider 后 dsh 会再给一整轮 5 次重试。最坏总耗时约 85s（5×5 + 5 + 5×5 + 5 + 5×5）。这是有意的「更顽强」，但确实是长时间等待；`modelRetryMaxRetries` / `modelSwitchDelayMs` 可调。
3. **`modelSwitchSkipCodes` 里 `QUOTA` 的语义**：`QUOTA`（HTTP 402）按账号余额处理，所以跳过同 provider 换模型。若将来 Kenari 出现「按模型的免费额度耗尽」语义，需要重新评估。
4. **重试与换模型的等待期界面上只有 `llm/retry` 节点**：升级阶段（换模型/回退）由插件自己 `await` 延时，不会生成 `llm/retry` 事件，界面上表现为一次失败的尝试后接一次新尝试。刻意不自己补写 `llm/retry` 事件——那会污染 `dsh-llm-retry` 的会话投影计数，风险大于收益。
5. **`system-prompt/assemble` 注入的 `provider` / `model` 变量仍是原选择**：`installModelSelection` 从 `selection.current` 取值，我们不改变它，所以系统提示词里模型自述的名字可能落后一轮。影响很小，记录在案。
6. **派生的只读路由（`/model` 命令等）看到的仍是会话原选择**：我们的 override 只作用于 `agent/request`，不写 `model/selection`。这是有意的——不让恢复机制篡改用户的持久选择。
7. **重试与换模型的完整链路没有端到端测试**：见 §7.d 的理由。代价是「dsh 升级后 `continue` 不再重跑 `prepareRequest`」这类宿主行为变化不会被本仓库的测试捕捉到；缓解手段是 §3.3 记录的行号锚点在升级时重读。

## 9. 不做的事

- 不给其他 provider 加恢复逻辑（§2 决策）。
- 不发「继续」消息（§2 决策）。
- 不实现插件自己的重试循环（§4.1 决策）。
- 不改 dsh 任何包，不 fork，不给 dsh 打 patch（最高纪律）。
- 不新增 web search / fetch 相关的恢复逻辑——那是 web seam 的事，已有 `KenariFirstSearch` / `KenariFirstFetch` 兜底链。
- 不补写 `llm/retry` / `llm/retry-started` 事件（§8.4）。

## 10. 实测修正（2026-09-13）：重试从未执行，重试权收回插件

本节是对上面若干结论的**推翻**，读 §4.1 / §8.2 / §8.4 / §8.7 / §9 时必须连这一节一起读。

### 10.1 实测到的事实

`~/.dsh/sessions` 下全部 8 个会话日志里 `llm/retry` 与 `llm/retry-started` 事件数都是 **0**。9 月 11 日那次：

- 失败是 `TRANSPORT`（`"Connection error."`，0 token），换模型通知在失败后 **9ms** 落地，下一次 `request/header` 在 **5015ms** 后发出 —— 正好一次 `modelSwitchDelayMs`，而不是 5 次固定 5s 的下限 25s。
- 该会话 `assistant/attempt` 只有 2 条（每个失败模型各一次），即每个模型只被尝试一次。
- §8.2 预估的最坏 85s 与实测每次切换 5s 相差一个数量级：**重试这一半根本没有生效**。

### 10.2 根因

`agent/request-error` 是**没有默认行为**的瀑布：不调用 `next()` 的监听器会否决它后面的一切。因此

1. 插件一旦处理某次失败，就同时把 `dsh-llm-retry`（和 compaction 等下游策略）全部饿死；
2. 只要注册顺序被翻过来一次（live patch / HMR 重载后重新注册），llm-retry 就永久出局，**而插件无法观察到自己的注册顺序**。

§4.1「重试交给 dsh 自带机制」在顺序正常时成立（探针与 `test/retry-repro.mjs` 场景 B 都验证了），但它把「用户拿得到 5 次重试」建立在一个插件既控制不了、也验证不了的运行期条件上。§7.d 只验证了策略形状，没有端到端复测，所以这个前提从未被检验。

### 10.3 改法

| 改动 | 位置 |
| --- | --- |
| 监听器先 `await next()`，链上已决定重试则原样放行；下游抛错记 warn 后继续本地恢复 | `src/llm/recovery.ts` |
| 重试权收回插件：新增阶段 0，同路由重试 `modelRetryMaxRetries` 次、间隔 `modelRetryDelayMs` | `src/llm/recovery.ts` |
| dsh 的重试在 Kenari 路由上关掉（`retryPolicy.maxRetries: 0`），插件自带适配器同用 `dshRetryDisabledPolicy()` | `cordis.patch.yml`、`src/llm/retry.ts`、`src/index.ts` |
| 重试预算**按路由**计算：换模型/回退后新路由拿完整一轮（dsh 的计数按 provider，换模型后直接是「用尽」） | `src/llm/recovery.ts` |
| 链上本轮已排程过重试（会话里出现过 `llm/retry`）时让位，两条机制不各数一遍 | `src/llm/recovery.ts` |
| 换模型排除本 step 里失败过的路由，修掉 glm-5-3-flash ↔ nemotron 那种同窗口来回横跳 | `src/llm/recovery.ts`、`src/llm/candidates.ts` |
| 新增 `modelRetryNoticeEnabled`（默认 `true`）：开始重试时注入一条说明，避免「没有理由的等待」 | `src/index.ts` |

### 10.4 被本节推翻/修订的原文

- §4.1「5s × 5 重试交给 dsh 自带的 `dsh-llm-retry`」→ 改为插件自己的状态机；「不自己写重试循环是刻意的」这条理由（界面上没有解释）由 `modelRetryNoticeEnabled` 的通知补上。
- §4.2 的两处 `retryPolicy` 写入点、以及「两个写入点需手工同步」→ 只剩一个来源：插件 Config。
- §8.2 的 85s 最坏耗时估算 → 现在每条路由 1 + 5 次尝试，随后升级，不再叠加 dsh 的一整轮。
- §8.4「界面上只有 `llm/retry` 节点」→ 现在重试也不产生 `llm/retry`（该路由的 dsh 重试已关），等待由通知解释；「不补写 `llm/retry` 事件」的决定不变。
- §8.7「完整链路没有端到端测试」→ 由 `test/retry-repro.mjs` 补上（真实 `dsh-llm` / `dsh-agent` / `dsh-session-projection` / `dsh-llm-retry` / `dsh-agent-loop` + 本插件，三个场景）。
- §9「不实现插件自己的重试循环」→ 撤销，理由见 §10.2。

### 10.5 验证

`pnpm build && node test/retry-repro.mjs`（三条边界）与 `pnpm test:model-recovery`：

- 场景 A（出厂配置）：每条路由 1 + 5 次尝试后才升级，`llm/retry` 为 0，重试有通知解释。
- 场景 B（该路由 dsh 重试开着、插件在内层）：llm-retry 重试 5 次，插件不叠加自己的预算。
